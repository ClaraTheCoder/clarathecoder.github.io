Neo is Vodafone's global design system, and the first to bring engineers into the core team alongside designers. Before this, design lived primarily in Figma, with different code implementations scattered across products and markets. I was brought in to help architect the core of Neo and build its React components, making sure it was scalable to every consumer, accessible to WCAG 2.2 AA, and tested across every brand, theme, breakpoint and locale.

## Tokens in layers

Our tokens are split into three layers: primitives, semantic tokens that say what each value is for, and a brand layer on top that only overrides what's different. Primitives hold the raw values, and semantic tokens give each one a job, like "primary background". Dark mode just points the same semantic tokens at different primitives, so a brand can override the primitives and still be able to use light and dark modes.

Creating a new sub-brand is easy, because nothing is hard-coded in the components. Consumers write a single file with the CSS variables they want to change (fonts, colours, border radii), and every component picks it up, with no need to restyle components through CSS classes. The tokens package is versioned, so if the design system team makes changes, consumers can choose when to update, without worrying that token changes will break a custom brand theme.

## Building our own pipeline

Originally, we built the token pipeline with a third-party service, but we outgrew it within a few months. Tokens couldn't be set per breakpoint, so we had to hand-roll our responsive typography at the component layer. We ran into bugs with CSS gradient tokens and with using the oklch colour space, and tokens weren't consistent from one platform to the next. So we built our own pipeline to handle everything we needed to pull from Figma.

This is done with a purely deterministic script (no LLMs as the tokens had to be exactly the same every time). The script uses Style Dictionary to push changes from Figma to a PR in three packages in the monorepo: plain CSS, Tailwind, and React Native.

Icons and illustrations are handled similarly: a script pulls changes from Figma and updates the icon and illustration packages. Icons come as plain SVG, React or React Native components. The script handles multi-colour icons too, so the main icon colour can match the text alongside it but meaningful colours such as the green bar on a full battery use the correct semantic tokens. Most illustrations come in light and dark mode, and they automatically switch to the right colour mode when used in our components.

## An accessible, global base layer

Have you ever had to build a date picker from scratch? It's a nightmare when you're building for one product, let alone when you need to support every product in a bunch of markets.

From day one on Neo, we knew we'd have to meet WCAG 2.2 AA, which the European Accessibility Act makes a legal requirement. We also needed the components to work in every market's language, including right-to-left support and locale-aware dates. I chose React Aria Components as our headless base layer because all of this is built in. This had to be decided before we built anything complex, because a base layer is hard to retrofit. For example, MenuList and ComboBox both open in the same Popover, so changing the base layer later would mean reworking both at once.

We wanted potential consumers to know that we weren't going anywhere, and they wouldn't need to do another migration in a year. React Aria was mature, stable, heavily tested for accessibility, and shipping new features and updates every month. Six months later, we had Neo externally audited for accessibility, and only a handful of issues were found across the entire component set. We were able to patch them in a few days.

## Testing every axis

Before Neo, designers had no single way to tell if their work had drifted, as components were spread across products and systems. We wanted to make sure what they signed off stayed exactly as they had intended, so we tested every theme, breakpoint and locale.

Every component has unit tests for its behaviour, with additional interaction and accessibility testing in Storybook. Visual regression runs against each story, too, in light and dark mode and at each breakpoint where the layout changes, and failure on any of these axes blocks the PR. Every component also has a right-to-left story with its own baseline snapshot. These tests caught real regressions before they made it to consumers: issues with modals not mirroring when portalled outside of the right-to-left provider, and fixes we needed to make to the bigger components when we updated the base buttons.

They can see the real code for each component in Figma and how it changes when they toggle props, because the full prop surface is mapped between Figma and code.
