[CaseMeta] Role: technical side of the Neo design team · Timeline: February 2026 to present · Platforms: web, React Native · Focus: accessible foundations, testing, core components, component metadata

- Hook (once): the handover. Before Neo, design handed Figma files to each market's teams, and each built them its own way, so the same component came out differently everywhere. Neo put engineers inside the design team: one team of engineers working closely with designers, building each component once for every brand, market and platform. Frame the old way as a handover model, not anyone's fault. Keep it to a few lines

## Context

- Neo is Vodafone’s new global design system, and the first with a shared React library
- Bridge (for everyone): building it once only works if that one build covers every combination of:
  - Brand: themed from one source
  - Theme: light and dark
  - Platform: web, then React Native
  - Breakpoint: four on web (React Native is mobile-only)
  - Locale: many languages, including right-to-left
- Each axis multiplies the others. The rest of the post is how the foundations keep that cheap
- One line on the team: I joined the design team in February 2026 to work on the technical side, and made the early engineering decisions (React Aria, the testing strategy, Button and form fields). Everything else in the post is "we"

## Tokens: from Figma to every platform

- The pipeline. Design owns tokens in Figma and Supernova; engineering takes over at the pull:
  - `tokens:pull` exports Style Dictionary JSON and commits it. It's deterministic, so a design change arrives as a reviewable diff in a pull request (ADR 0025)
  - Style Dictionary builds every platform output in-project, from that one committed source, so web and React Native can't drift

- The tiers: primitives (raw palette) → semantic (background, text, border: what a colour is for) → components, which only ever read semantic tokens
- Base and sparse overlays (ADR 0033): one complete base tree, and every other value is an overlay holding only what it changes

- [StatGroup] Complete trees for every combination: 2 themes × 4 breakpoints = 8, multiplied again by every brand. With overlays, each new value is one more set of files
- A collision between two overlays fails the build rather than silently winning
- Brand is the payoff: a new brand is a new set of token files that overrides specific semantic tokens. Because components only read semantic tokens, every component re-skins with no component code changed, and the brand still composes with light and dark
- Packaged to adopt separately: tokens only (plain CSS, a Tailwind mapping layer that only points at those variables (ADR 0032), or React Native), components with Neo's tokens, or, on web, components with your own token values via the `--neo-*` custom properties. One line, then a forward link to the trust post for how teams moved between them
- Cut if over length: the `--neo-` prefix (ADR 0034) stops a host page's own variables colliding with Neo's and re-theming it by accident
- Light/dark doesn't stop at colour, so `Image` takes a `dark` source too

## One component contract, two platforms

- The same base-and-overlay idea one layer up: each component's contract is a shared file plus sparse web and React Native overlays (ADR 0060)
- Shared fields flow to every platform, so differences are explicit and listed with a reason (e.g. `testID` vs `data-testid`)
- Figma links straight to code: every stable component has Code Connect with full prop mapping (ADR 0020), so an engineer looking at a design sees which component to use and with which props

## An accessible, global base layer

- React Aria Components as the headless primitive layer (ADR 0013). Global adoption sets two non-negotiables:
  - Accessibility: WCAG 2.2 AA, required by law
  - Internationalisation: keyboard, focus, RTL and locale-aware dates handled once, for every market
- React Aria derives direction from the locale, so RTL is handled inside the component tree. DatePicker and Calendar handle calendar systems (Gregorian, Hijri, Buddhist, Persian) and locale formatting. React Native follows its own platform model for right-to-left (ADR 0055)
- Why not the alternatives, in a line or two: Radix had no DatePicker or Calendar primitive and layout-only RTL, so date formatting and calendar systems would have been ours to build; Base UI had momentum but no track record yet
- For good: a base layer chosen to last
  - React Aria is backed by Adobe, which stakeholders brought up in meetings unprompted, and it's the most thoroughly accessibility-tested option. Radix development was slowing
  - [Callout: impact] The external accessibility audit: a handful of minor issues, all patched within days

## Testing every axis

- Unit tests for behaviour, accessibility checks on every documented example, visual snapshots in real browsers (ADR 0012). A failing accessibility check blocks the merge
- Web visual tests run per theme × breakpoint on every PR, plus a right-to-left pass: one Arabic-locale story per component, about 80 baselines (light mode only, so don't claim RTL × theme). React Native has its own tiers, with visual regression in light and dark on an Android emulator. Keep the platform difference to one line
- Pays off the hook: designers had seen their work drift once it was built. Visual regression on every PR means what they sign off stays as signed off. One line; the trust post covers it as working in the open
- Caught real regressions when later, more complex components needed changes to Text, Link, Button and Popover
- [Callout: finding] The first RTL run caught a real consumer bug: Modal, FullScreenModal and MegaMenu didn't mirror. React Aria handles direction inside the tree, but overlays render into `<body>`, outside the element where the provider sets `dir` and `lang`. Dark mode had hit the same issue and been patched per overlay; direction never had. Overlays now re-apply direction and language alongside colour mode, guarded by a unit test and the baselines

## Close

- Once: one engineering team working with design, so a component is built once and behaves the same everywhere
- For everyone: many brands, many products, one system. Brand is a set of token files; light and dark, RTL and i18n, and breakpoints are tested on every change
- For good: more than 60 ADRs record why each decision was made, so the next maintainer doesn't have to rediscover it. One review checklist tags every rule with who checks it: CI, an LLM pass or a person. Don't claim the PR-comment bot is live (ADR 0028 is proposed)
